# 2026-09-08 — niyama v1.0.9 P(-1) Security Audit

**Auditor**: Claude (Opus 5) — under user direction.
**Scope**: niyama v1.0.8 source (commit `0cd1d8e` + the v1.0.8 toolchain
release). All 5 engines (`bre`, `re2`, `pcre`, `fuzzy`, `vim`) plus the
shared modules `src/posix_classes.cyr` and `src/unicode_props.cyr`.
**Methodology**: per
[CLAUDE.md § Security Hardening](../../CLAUDE.md#security-hardening-before-every-release)
and [first-party-standards § Security Hardening](https://github.com/MacCracken/agnosticos/blob/main/docs/development/applications/first-party-standards.md#security-hardening-new--required-before-every-release).
8 mandatory items walked. Review ran as a 6-dimension parallel pass
(buffer safety, PCRE2 CVE corpus, Pike-NFA correctness, fuzzy/shared,
parallel codepaths, optimization) followed by an adversarial refutation
pass; 32 raw findings, 3 refuted, 29 confirmed. **Every finding recorded
below was independently reproduced with a compiled probe against the real
source before any repair was written.**

## Headline

**One CRITICAL and eight HIGH findings — all fixed in v1.0.9.** This is a
material change from the v0.9.0 audit, which found no CRITICAL/HIGH
issues. The difference is method, not regression: v0.9.0 audited by
reading; this pass built probes and measured, which is what surfaced the
heap overflow and the three unbounded-allocation defects.

| Severity | Count | Status |
|---|---|---|
| CRITICAL | 1 | fixed |
| HIGH | 8 | fixed |
| MEDIUM | 6 | fixed |
| LOW | 6 | 5 fixed, 1 documented |

niyama's structural defences still hold and are worth restating: no JIT
(avoids the CVE-2019-20454 class entirely), no filesystem access (no path
traversal), no subprocess execution (no command injection), and the three
Pike-NFA engines structurally cannot catastrophic-backtrack.

## C1 — CRITICAL — heap out-of-bounds write via a crafted pattern

**Where**: `src/pcre.cyr` `_pcre_apply_simple_q` (`?` branch), and the
identical shape in `src/re2.cyr`, `src/vim.cyr`, `src/bre.cyr`.

**What**: `_<engine>_emit_raw` is the only place that enforces
`MAX_INSTRS`. The quantifier and alternation paths do not grow the program
through `_emit_raw` — they call `_<engine>_shift_right`, which memmoves the
instruction range right by one slot, and then increment `_instr_n`
directly. The `?` branch performs no emit at all afterwards, so nothing
ever checked the ceiling and `_instr_n` grew without bound, one slot per
nesting level.

The NFA is a single allocation of `header + instr_bytes + class_bytes +
name_bytes` = 256 + 65 536 + 2 048 + 360 = **68 200 bytes**, with the
instruction region at its head. Once `_instr_n` passed ~4 245 the shift
wrote past the end of the allocation; before that it corrupted the class
bitmaps and name table, which live in the same allocation.

**Reproduced**: pattern `"(?:" × 400 + "a" × 4095 + ")?" × 400`.

```
MAX_INSTRS      = 4096
final instr_n   = 4496          <-- 400 slots past the ceiling
OVERRUN         = 6400 bytes past the instruction region
```

The independent probe run for this audit and the reviewing agent's probe
agreed. The agent's probe additionally showed the leaked instruction words
(`0x6101` = `PCRE_OP_CHAR | ('a' << 8)`) appearing inside a *subsequent*
`alloc()` result — so code that reasonably assumes a fresh allocation is
zeroed would read attacker-influenced bytes.

**Why the test suite missed it**: `niyama_pcre_compile` still returns 0
with `PCRE_E_TOO_LARGE`, because the trailing `_pcre_emit_save(1)`
eventually trips the emit guard. The API result looks correct; the heap is
already corrupt.

**Impact**: this is CLAUDE.md's own CRITICAL example — "heap overflow via
crafted pattern" — and it lands on `re2`, the engine daimon-orchestrated
agents use as a DoS-safe gate over untrusted input.

**Fix**: a `_<engine>_instr_n >= <ENGINE>_MAX_INSTRS` ceiling check before
every shift-based growth site — 16 sites across the four engines (bre 2,
re2 4, pcre 5, vim 5). `TOO_LARGE` is an existing frozen error code and the
parsers already propagate `_err`, so the public behaviour is unchanged for
every pattern that was already accepted. Verified: `instr_n` now stops at
exactly 4096 and the pattern is rejected cleanly.

## C2 — HIGH — unbounded, unreclaimable heap growth (three distinct sites)

`alloc()` (lib/alloc.cyr) is a pure bump allocator: `_heap_ptr` only
advances, and the sole reclaim path, `alloc_reset()`, invalidates every
pointer ever handed out — so a library holding caller-visible NFA handles
can never call it. Every `alloc()` on a per-call path is therefore a
permanent leak.

**C2a — `_<engine>_pike_run` allocated two 160-byte scratch arrays per
call, and is called once per START POSITION of a search.** An N-byte
unanchored search permanently retained 320·(N+1) bytes.

```
re2, pattern "Z", subject 20 000 x 'a' (no match)
  before: heap delta = 6 400 320 bytes   (exactly 320 per input byte)
  after:  heap delta = 0
```

**C2b — pcre's backtracker allocated a 160-byte save snapshot at every
executed SPLIT / LOOKAHEAD / NLOOKAHEAD / LOOKBEHIND / RECURSE**, bounded
only by the 1M step limit.

```
pcre, pattern "(a+)+b", subject 24 x 'a' (no match, 1 000 025 steps)
  before: heap delta = 45 715 840 bytes
  after:  heap delta = 0
```

**C2c — `_pcre_run_at` allocated the top-level saves array per call**,
i.e. once per start offset of a search.

**Fix**: all three hoisted to process-lifetime buffers allocated once in
`_<engine>_lazy_init`, alongside the matcher scratch that already lived
there. Each is fully re-initialised at the top of every run, so sharing is
behaviour-identical. pcre's per-backtrack snapshots became a
depth-indexed pool sized `(PCRE_MAX_DEPTH + 2) × PCRE_MAX_SAVES × 8`;
each snapshot's lifetime is confined to one iteration at one depth
(take → recurse → restore) and at most one is live per depth, so one slot
per depth suffices.

## C3 — HIGH — the documented catastrophic-backtracking guard was
(len+1)× weaker than advertised

`_pcre_run_at` reset `_pcre_step_count = 0` on entry, and
`niyama_pcre_search_at` calls it once per start offset. The effective
budget for a search was therefore `_pcre_step_limit × (len + 1)`, not the
documented 1 000 000. On a 4 KB subject that is 4 billion steps.

**Fix**: the reset moved into a new `_pcre_begin_match()` called once per
public entry point (`niyama_pcre_match`, `niyama_pcre_search_at`), so one
budget now spans the whole operation. `niyama_pcre_set_step_limit()` and
`niyama_pcre_last_step_count()` are unchanged.

## C4 — HIGH — `{n,m}` compiled by re-parsing, corrupting captures

`_<engine>_apply_brace_q` implemented repetition by rewinding the source
cursor and re-running `_parse_primary` once per copy. That function has
non-idempotent parser side effects, so each repetition burned one capture
index, one name-table slot and one class bitmap. Re-parsing was also
re-entrant, which clobbered the shared `_q_splits` scratch for nested
quantifiers.

Reproduced, all four engines:

| Pattern | Before | Correct |
|---|---|---|
| `(?:a{1,2}){1,2}` vs `"aa"` | no match | match |
| `(a){2}(b)` vs `"aab"` | group 2 = the second copy of `a` | group 2 = `b` |
| `(a){10}` | rejected `SYNTAX` | compiles |
| `(?<x>a){2}` | rejected `DUPLICATE_NAME` | compiles |

The `re2` case is the worst: a nested-quantifier deny-rule in a daimon
pattern gate silently stops matching, i.e. **the gate fails open**, and
`last_error()` is 0 so the caller has no signal.

**Fix**: the compiled atom is snapshotted once into `_<engine>_tmpl` and
repetitions are appended as relocated copies (`_tmpl_save` /
`_tmpl_append`), so no parser state is touched per repetition. Branch
targets inside `[lo, lo+n]` shift by the copy delta; pcre's copier mirrors
`_pcre_shift_targets_one`'s branch set exactly, including COND (whose arg1
is a group index, not a pc). Removing the re-parse also removes the
re-entrancy, which fixes the `_q_splits` clobber by construction.

**Related**: the split list was sized 64 while all four engines advertise
`n_max > 1000` as the rejection threshold, so `{0,65}`..`{0,1000}` were
falsely rejected `TOO_LARGE`. Capacity is now `<ENGINE>_MAX_QSPLITS = 1000`,
with `MAX_INSTRS` remaining the real backstop.

## C5 — MEDIUM — `niyama_fuzzy_search` returned an out-of-range offset

Under `FUZZY_FLAG_UNICODE_NFD` the returned offset indexed the *normalized*
scratch buffer, not the caller's string. With a subject of five U+00E9
followed by `"dog"` (13 bytes), it returned **15** — past the end of the
caller's string. A caller slicing at that offset reads out of bounds.

**Fix**: `_fuzzy_norm_to_orig` walks the original a codepoint at a time,
accumulating each one's decomposed byte length, and translates the offset
back. Canonical reordering permutes combining marks within a sequence but
never across a starter and never changes the total byte count, so
boundaries computed this way agree with `str_normalize`. Verified: now
returns 10, and the result is clamped to the subject length regardless.

## C6 — MEDIUM — silent truncation instead of an error

Every `_fuzzy_dp_*` entry clamped an over-long subject to
`FUZZY_MAX_TEXT_LEN`, so a match past byte 4096 reported "no match" with
`FUZZY_E_OK` — indistinguishable from a genuine miss. NFD made it reachable
*inside* the documented limit, because decomposition expands the subject.

**Fix**: new `FUZZY_E_TEXT_TOO_LONG = 4`, checked after normalization on
all four public entry points. `niyama_fuzzy_match` additionally rejects the
negative error distance, which would otherwise have satisfied
`d <= max_edits` and reported a **false positive match**.

## C7 — MEDIUM — vim `\>` fired at word starts

`\<` and `\>` both compiled to `VIM_OP_BOUNDARY`, the symmetric `\b` test,
so each fired at both ends of a word. `\<foo\>` only looked correct because
each end is independently a boundary. Reproduced: `\>x` matched `"x"` at
position 0.

**Fix**: `VIM_OP_WORDBEGIN` (15) and `VIM_OP_WORDEND` (16) with the strict
left/right tests bre has had since v0.7.0.

---

## C8 — MEDIUM — `\K` inside a lookaround moved the outer match start

Save slot 0 is the match start, not a user capture. A `\K` inside a
positive lookahead or lookbehind emits `SAVE 0`, and positive lookarounds
deliberately keep their sub-captures — so the outer match start was rewritten
to a zero-width position inside the lookaround, producing an inverted
group-0 span (start > end).

**Fix**: slot 0 is restored from the snapshot on the positive-lookaround
success path, scoping `\K` to the lookaround as PCRE2 does. Top-level `\K`
is unchanged.

---

## C9 — LOW — unvalidated `from` on all four `search_at` entry points

`niyama_<engine>_search_at(nfa, s, len, from)` assigned `var i = from`
with no check. A negative `from` ran the matcher backwards off the front of
the subject buffer. Note the v0.9.0 audit's input-validation table asserted
`if (from > len)` checks were "present"; they were not. (`from > len` is in
fact harmless — the loop simply does not execute — so the real hole was
only the negative case.)

**Fix**: `if (from < 0) { return 0 - 1; }` and the same for `len`, on all
four engines.

---

## C10 — LOW — unchecked `alloc()` results

`alloc()` returns 0 on exhaustion. Every lazy-init pointer was dereferenced
unconditionally, turning heap exhaustion into a write to the NULL page.

**Fix**: all 33 lazy-init allocations across the five engines are checked;
on failure the engine sets its `TOO_LARGE` error and returns *without*
setting the init flag, so a later call retries rather than running on
half-initialised state.

---

## Known limitation — pcre recursion depth (documented, not fixed)

`_pcre_match_run` recurses natively for SPLIT and SAVE, so recursion depth
scales with **input position**, not with pattern nesting. With
`PCRE_MAX_DEPTH = 256`, a quantifier that must consume more than ~250
positions exhausts it and the match fails.

```
a*$        over 300 x 'a'   -> no match   (correct answer: match)
(a){200}   over 200 x 'a'   -> no match   (correct answer: match)
(a){100}   over 100 x 'a'   -> match
```

Confirmed pre-existing (identical on v1.0.8). The limit is **not a
tunable**: measured against an 8 MB stack, `_pcre_match_run` frames are
roughly 20 KB and the process SIGSEGVs somewhere past ~400 frames, so 256
is already close to the ceiling. Raising it trades a false negative for a
crash.

Removing the limit requires replacing native recursion with an explicit
heap-allocated backtrack stack — a rewrite of the matcher core, too large
to carry safely in a patch release alongside this many security fixes.

**Mitigated for v1.0.9** by making the condition *observable*: new
`PCRE_E_DEPTH_EXCEEDED = 12`, set when either depth guard fires and
readable via `niyama_pcre_last_error()` after a match or search. A caller
can now distinguish "no match" from "gave up". Tracked for the next minor.
