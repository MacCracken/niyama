## G. Step 4 — PCRE2 CVE cross-check + domain coverage

### G1 — PCRE2 CVE corpus cross-check (no findings, all defended)

Reviewed niyama_pcre against canonical PCRE / PCRE2 CVE patterns:

| CVE class | Pattern | niyama defense |
|-----------|---------|----------------|
| **CVE-2015-2326** | Lookbehind width OOB in `find_fixedlength` | `_pcre_compute_width` is conservative — sums known-1 or known-0 widths only; rejects unknown opcodes with `-1` (varwidth). |
| **CVE-2017-7186** | UTF-8 + grapheme cluster OOB | `_uc_decode_utf8` returns 0xFFFD step=1 on truncation/invalid; matchers treat 0xFFFD as literal cp. No `\X` grapheme operation. |
| **CVE-2017-11164** | Recursion limit not honored | `_pcre_depth_limit = 256` checked at every recursive `_pcre_match_run` entry; `_pcre_step_count` checked at every dispatch step (default `_pcre_step_limit = 1M`). |
| **CVE-2016-3191** | Backref + case-fold OOB | niyama backref is byte-compare (1:1), no length change between captured and matched. |
| **CVE-2014-9769** | Named group MAX_NAME_SIZE | `PCRE_NAME_MAX_LEN = 31` checked in `_pcre_add_name`; longer rejects with `PCRE_E_TOO_LARGE`. |
| **CVE-2015-3217** | `(?R)` infinite recursion | `_pcre_step_count` increments at every step; bails at `_pcre_step_limit`. Independent depth-bound also fires at 256. |
| **CVE-2019-20454 et al.** | JIT memory protection | N/A — niyama is interpreter-only, no JIT. Whole class structurally avoided. |

Defenses are layered (step + depth + width-analysis). A finer
audit happens in step 5; this is the first-pass cross-check.

### G2 — re2 POSIX bracket class gap (MEDIUM, NEW)

**Finding**: `niyama_re2` doesn't support POSIX bracket classes
`[[:alpha:]]`, `[[:digit:]]`, etc. bre, pcre, and vim all do (per
v0.7.0 + v0.8.0 work). re2 was missed in the v0.7.0 carve — ADR
0007 documented the additions for bre/pcre/re2 but didn't include
POSIX classes for re2.

**Impact**: real cross-engine consistency gap. Patterns that
compile under bre/pcre/vim with `[[:alnum:]]` would fail under re2
with a syntax error. Consumer-visible.

**Cost to fix**: small — re2 already has class parsing; needs the
same `_posix_match_class_name` hook pcre uses, ~10 lines in
`_re2_parse_class`. posix_classes.cyr is already included by
re2's tests.

**Decision needed**: primary (v0.9.0 step 6) or remainder (v1.0
sweep)? Argument for primary: cross-engine surface should be
consistent at freeze. Argument for remainder: it's a feature
addition, not a hardening fix.

### G3 — Long property names + `\p{Greek}` script properties (LOW)

`\p{Letter}` (long aggregate name) and `\p{Greek}` (script
property) not supported. Documented in `unicode_props.cyr` as
out-of-scope for v0.8.0. v1.0 remainder candidate (post-fold
extension if a consumer asks).

### G4 — Absolute anchors `\A` / `\z` / `\Z` (LOW)

PCRE2 has `\A` (string start), `\z` (string end), `\Z` (string
end allowing trailing `\n`). niyama uses `^`/`$` strict-default
(equivalent to `\A`/`\z` for our purposes since we don't honor
multi-line `^/$` without `(?m)`). Document as a portability note
rather than implementing parallel syntax.

**Action**: doc note in `state.md` flavor rubric. v1.0 sweep.

### A1 — fuzzy lacks `_search_at` (LOW)

bre / re2 / pcre / vim all expose `niyama_<engine>_search_at(nfa,
s, len, from)` for "search starting at offset `from`". fuzzy
doesn't. Consumers wanting fuzzy-search-from-offset must slice the
input themselves.

**Action**: defer. Adding it is a real change to the substring DP
(needs to anchor at `from`); risk near freeze > value. Document
the gap in `state.md` flavor rubric. Post-fold candidate.

### A2 — `compile_opts` asymmetry (LOW)

Only fuzzy (max_edits, flags) and vim (mode) expose `_compile_opts`.
bre, re2, pcre have only `_compile`. If post-v1.0 needs
flags-on-compile for the linear-time engines, that's a new ABI.

**Action**: document, don't fix. Frozen-as-is is fine through v1.0.

## B. Architectural duplication

### B1 — Class-bitmap helpers duplicated 4× (LOW)

`_<engine>_class_set`, `_class_range`, `_class_invert`, `_class_get_at`
exist in bre, re2, pcre, vim — same byte-bitmap operations. ~60
lines × 4 engines.

Engines have minor quirks:
- `re2` lacks `_class_invert` (negation handled in opcode dispatch).
- `pcre` adds `_class_set_folded` and `_class_range_folded` for
  ASCII case-fold inside char classes.

**Action**: skip extraction for v0.9.0. ADR 0007's "v0.9.0 cleanup"
language was specifically about vim → posix_classes (already done in
v0.8.0). Class-bitmap extraction would land near surface freeze with
nontrivial regression risk; the 240-net-line savings doesn't justify
the risk. Document as post-fold opportunity.

### B2 — Word-char / boundary helpers duplicated 3× (LOW)

`_<engine>_at_word_char` in bre, vim, pcre (re2 inlines the check).
`_<engine>_is_boundary` in vim, pcre (bre inlines). ~10 lines per
engine.

**Action**: skip. Too small to justify extraction risk.

### B3 — Opcode emit helpers duplicated 4× (BY DESIGN)

Per ADR 0009: "no shared kernel." `_<engine>_emit_raw / _op /
_char / _class / _save / _jmp / _split` per engine is the explicit
architectural decision. Not a finding.

### B4 — `pcre.cyr` in-loop saves alloc (MEDIUM)

`_pcre_match_run` calls `alloc(PCRE_MAX_SAVES * 8)` (160 bytes) at
**6 sites**: SPLIT, LOOKAHEAD, NLOOKAHEAD, LOOKBEHIND, RECURSE,
plus the top-level entry. For deeply nested or heavily-alternating
patterns, each match invocation can produce many such allocations.

**Concern**: not a correctness bug — Cyrius's bump-style `alloc()`
is fast — but for long-running consumers (cyim editing a large
file) this fragments. A `_pcre_saves_pool` indexed by recursion
depth would replace allocation with O(1) reuse.

**Action**: list as **step 6 candidate**. Confirm with bench
diff (step 7) whether the optimization is measurable; if not,
defer to post-fold.

## C. Edge cases / test coverage gaps

### C1 — Boundary tests for MAX_* limits (MEDIUM)

`MAX_INSTRS = 4096` (all four regex engines), `MAX_CLASSES = 64`,
`MAX_SAVES = 20`, `MAX_NAMES = 9` (re2/pcre). Patterns at exactly
the boundary, and at boundary+1, should error cleanly with
`*_E_TOO_LARGE`.

**Action**: add in step 6. Per-engine boundary test group. Important
for v1.0 since these limits are part of the frozen contract.

### C2 — `(?i)ß` ASCII-only-fold semantics (LOW)

ADR 0008 + v0.8.0 ship 1:1 case folding only (full case folding
deferred). `(?i)ß` matches `ß` (and `ẞ` if a single-cp uppercase
exists), but **not** `SS`. Documented; **not asserted in tests**.

**Action**: add a test in step 6 locking the semantics. Prevents
silent regression if someone later hooks `unicode_fold` (full-fold)
into the `(?i)` path without an ADR.

### C3 — Invalid UTF-8 input (MEDIUM)

`_uc_decode_utf8` returns `0xFFFD` (replacement) and advances 1
byte on invalid sequences. Matchers should handle without crashing
or infinite-looping. **Currently no fuzz coverage of invalid-UTF-8
input** — fuzz harnesses generate random patterns, not random
inputs.

**Action**: add fuzz seeds with deliberately invalid UTF-8 input
strings (lone continuation bytes, truncated sequences,
overlong encodings) in step 6. CRITICAL for security-audit
coverage.

### C4 — Recursion + lookaround nesting (LOW)

`_pcre_recurse_stop_pc` save/restore inside `LOOKAHEAD` /
`NLOOKAHEAD` / `LOOKBEHIND` / `ATOMIC` recursive calls is correct
by inspection. **No test exercises the nesting** — pattern like
`(?<=foo)(?P>g)x(?<g>...)` would.

**Action**: add 2-3 nested-recursion tests in step 6.

### C5 — Empty pattern (LOW)

`niyama_<engine>_compile("")` — POSIX says "matches everywhere
with empty match." Need to verify all 5 engines agree, then test.

**Action**: spot-check in step 6, add per-engine empty-pattern
test if behavior is consistent.

## D. Correctness verification (no findings)

Sampled and confirmed correct:

- **D1**: Null-pointer checks at every public API entry across all
  engines. `if (nfa == 0) { return ...; }` consistent.
- **D2**: Bounds checks before `load8(input + pos)` in all matchers.
  Spot-checked re2, pcre, vim main loops; all guard with
  `pos < input_len` upstream.
- **D3**: pcre step-limit guard increments on every dispatch step.
  Bail returns -1 (honest mismatch).
- **D4**: re2 + vim codepoint-stepping outer loop terminates on
  `pos > input_len`. Off-by-one verified.
- **D5**: Frozen error code numbers preserved per ADR rules.
  bre 0-4, re2 0-8, pcre 0-11, fuzzy 0-3, vim 0-5. New codes
  always at next-available slot.

A more thorough audit lives in step 5 (`docs/audit/`).

## E. Optimization observations (from step 2 bench)

### E1 — `re2_search_class` at 148µs (LOW)

Highest per-iteration cost in the matrix. Pike NFA per-byte
class-lookup hot. `_re2_class_get_at` does:
```
var off = class_base + ci * 32 + (c >> 3);
return (load8(off) >> (c & 7)) & 1;
```
Already minimal. Hot may be in the thread queue dispatch around it.
Profiling-guided optimization candidate for post-fold.

### E2 — `bre_search_dot_star` at 102µs (LOW)

`.*` worst-case Pike NFA — every position queues a thread. Expected.
No action.

### E3 — re2 vs pcre literal search gap (DOCUMENTED)

`re2_search_literal` (41µs) vs `pcre_search_literal` (17µs) — 2.4×.
Architectural: codepoint-stepped Pike NFA threads vs. byte-stepped
backtracking with fast-bail. Documented in `benchmarks.md`. Not a
regression.

## F. Documentation gaps

### F1 — `docs/architecture/` is empty (MEDIUM)

Per first-party-documentation, non-obvious constraints belong in
`docs/architecture/NNN-*.md`. Several niyama constraints qualify:

- The codepoint-stepping vs. byte-stepping split (re2/vim are
  cp-stepped; pcre is byte-stepped; fuzzy is byte-DP'd).
- Why each engine has its own opcode set (per ADR 0009 "no shared
  kernel").
- The save-table layout (`save[2N]` = group N start, `save[2N+1]`
  = group N end; `save[0]` = match start, `save[1]` = match end).
- The `lib/unicode/` dependency surface (categories, casefold,
  normalize) and the fold-time consumer expectation.

**Action**: write 3-4 architecture notes in step 8 (doc audit).
